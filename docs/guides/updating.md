# Updating the core

A project generated by the installer records the template release it came from.
`npm run core:update` brings the core files up to a newer release, reapplies the
identity of the product, and leaves every file the product owns alone. A core file
the team edited is kept and reported, never overwritten.

## Which projects can update

Only projects generated by the installer from the release that introduced the update
metadata onward. A clone of the template, or a project generated by an older
installer, has no `.dash/` directory, and every update command stops with:

```
.dash/core.json was not found. Only projects generated with the update metadata can run this command
```

There is no migration command for older projects.

## The update metadata

The installer writes `.dash/` once the project has its final bytes: after the rebrand,
the pruning of the template-only files, the locale, the palette and the env files, and
before `npm install` and the first commit.

| File                 | What it holds                                                                                                                                                                                                                                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `.dash/install.json` | The template version, the identity (name, slug, description, email), the token map of the rebrand and its values, the excluded and preserved paths, the removed paths, sections, lines and workflow jobs, the locale, the palette and `removedCapabilities` (empty at install, `["showcase"]` after `npm run remove:showcase`) |
| `.dash/core.json`    | The upstream `repository`, the installed `version`, the `core` and `userOwned` globs, and a `sha256:` checksum of every core file                                                                                                                                                                                              |

- **No secrets.** The keys of the project live in the env files only. Neither file
  holds an env value, a signing key, a webhook secret or a provider key.
- **Commit it.** The installer's first commit includes `.dash/`. `core:update` rewrites
  `core.json` and `remove:showcase` rewrites both files; commit them with the files they
  describe. A checkout without them cannot update.
- **Do not edit it by hand.** Both files carry `schemaVersion: 1`; a file with another
  schema version is refused, and a corrupt one stops the command with the name of the
  bad field.
- The directory is always `.dash`, whatever the product is called.

## Core and product files

`.dash/core.json` decides which files an update may touch. A path that matches a
`userOwned` glob is never written, even when it also matches a `core` glob.

| Core: replaced while untouched                                                                                | Product: never written                                                                                                            |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `apps/api/app/**`, `apps/api/start/**`, `apps/api/config/**`, `apps/api/database/**`, `apps/api/resources/**` | `apps/api/app/features/**`, `apps/api/tests/functional/features/**`                                                               |
| `apps/api/tests/unit/**`, `apps/api/tests/functional/**`                                                      | `apps/web/src/features/**`, `packages/ui/src/custom/**`                                                                           |
| `apps/web/src/**`, `apps/web/vite.config.ts`, `apps/web/tsconfig*.json`, `apps/web/index.html`                | `.env*`, `openspec/**`, `docs/**`, `README.md`                                                                                    |
| `packages/ui/**`, `packages/core-tools/**`                                                                    | `package.json`, `apps/api/package.json`, `apps/web/package.json`, the lockfiles, the Dockerfiles, the Compose files, `.github/**` |

A path that matches neither list (`e2e/`, `plugins/`, `apps/api/commands/`, the root
configuration files) is outside the update: it is never written and never reported.

## Check, preview and update

Run from the project root. Arguments go after `--`.

```bash
npm run core:check                                # what an update to the latest release would change
npm run core:update -- --dry-run                  # the same, worded as an update preview
npm run core:update                               # apply it
npm run core:check -- --to 0.2.0                  # compare with a given release
npm run core:check -- --source ../template    # compare with a local checkout of the template
```

| Option                | Commands          | Effect                                                                                                                          |
| --------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `--to <version\|ref>` | `update`, `check` | The release to compare with. Default: the latest GitHub release of `repository`                                                 |
| `--source <dir>`      | `update`, `check` | Use a checkout of the template on this machine instead of a download. Without `--to`, its root `package.json` names the version |
| `--dry-run`           | `update`          | Print what would change and write nothing                                                                                       |
| `--help`              | every command     | Print the usage of the command                                                                                                  |

What one run does:

1. Reads `.dash/core.json` and `.dash/install.json`.
2. Resolves the target release: `--to`, or the latest release of `repository`.
3. Downloads the release into a temporary directory with `giget`, or copies the
   `--source` checkout there without its excluded paths.
4. Replays the installer on the copy: the excluded paths, the removed sections and
   lines, the token replacement (except on the preserved paths, `packages/core-tools/**`),
   the removed paths and workflow jobs, the locale, the palette, and every capability
   of `removedCapabilities`. The copy now reads like the project would had it been
   generated from that release, so a project generated as "Acme AI" still says
   "Acme AI" after the update, with its own locale and palette.
5. Compares every core path through three checksums: the recorded one, the one on disk
   and the one of the release.
6. `core:update` only: writes the result as one transaction, with `packages/core-tools/**`
   after every other file and `.dash/core.json` last.
7. Prints the report and removes the temporary directory.

## The report

| Your file                               | The release                       | Result                                    | Heading of the report                       |
| --------------------------------------- | --------------------------------- | ----------------------------------------- | ------------------------------------------- |
| Untouched                               | Changed                           | Replaced; the new checksum is recorded    | `Updated`                                   |
| Untouched                               | Deleted                           | Deleted                                   | `Deleted`                                   |
| Absent                                  | Adds it                           | Written                                   | `Added`                                     |
| Untouched                               | Unchanged                         | Nothing                                   | —                                           |
| Edited                                  | Changed                           | Kept; the old checksum stays recorded     | `Modified locally, kept as they are`        |
| Deleted                                 | Changed                           | Kept deleted, marked `(deleted locally)`  | `Modified locally, kept as they are`        |
| Edited                                  | Deleted                           | Kept, marked `(deleted upstream)`         | `Modified locally, kept as they are`        |
| Edited                                  | Unchanged                         | Kept, not reported                        | —                                           |
| Edited to the same bytes as the release | —                                 | Nothing; the release checksum is recorded | —                                           |
| Created by you, not recorded            | Adds the same path, other content | Kept                                      | `Conflicts, kept as they are`               |
| Created by you, not recorded            | Does not have it                  | Kept                                      | `Not tracked by the core, kept as they are` |

The version in `.dash/core.json` advances even when files are kept.

The root, API and web `package.json` files belong to the product, so an update never
writes them. When the release adds or changes an entry of their `scripts`,
`dependencies`, `devDependencies`, `imports` or `engines`, the report lists it under
`Manifest changes in the release (apply them by hand, then run npm install)`. Entries
the project added itself are not listed. The note repeats on every run until the
manifest matches the release. `packages/ui/package.json` and
`packages/core-tools/package.json` are core files: when an update replaces them, run
`npm install`.

Exit codes:

| Command                    | Exits 0                                     | Exits 1                                                                                          |
| -------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `core:check`               | Nothing is pending                          | A file to write or delete, a kept file, a conflict or a metadata refresh is pending; or an error |
| `core:update -- --dry-run` | Nothing is pending                          | Same as `core:check`                                                                             |
| `core:update`              | Everything was applied and no file was kept | A modified or conflicting file was kept (the rest was applied); or an error                      |

Files listed as not tracked and manifest notes do not change the exit code.

## Resolve a kept file

A file under `Modified locally, kept as they are` was changed by the team and by the
release. It is reported by every update to a release that differs from the version
recorded for it.

- **Take the release.** Put the file back to the bytes the core recorded, for example
  `git checkout <commit-before-your-edit> -- <path>`, and run `npm run core:update`
  again: the file is untouched now, so it is replaced. Move the customization into a
  feature folder ([extending](./extending.md)).
- **Keep yours.** Merge the change of the release by hand. The file stays reported, and
  `core:update` exits 1, until its bytes match the release.

A conflict is a file you created where the release now adds one: rename yours, or
delete it and run the update again.

## Release tags

- A release is a tag `v<version>` of the template repository. `--to 0.2.0` and
  `--to v0.2.0` both select the tag `v0.2.0` and record `0.2.0`; any other ref (a
  branch, a commit) is used and recorded as written. A ref starts with a letter or a
  digit, holds only letters, digits, `.`, `_`, `/` and `-`, and never `..`.
- Without `--to`, the updater reads the latest release of `repository` from the GitHub
  API and refuses an answer that belongs to another repository.
- `repository` is `github:<owner>/<name>` or `https://github.com/<owner>/<name>`; other
  hosts are refused.
- `--source <dir>` needs no network. The template's CI uses it to check a project
  generated from the same checkout: `npm run core:check -- --source "$GITHUB_WORKSPACE"`
  must report no changes.

## Safety

- The release is downloaded and transformed before a single project file is written.
  A download, transformation or path failure exits 1 and leaves the project as it was.
- A path that is absolute, has a `..` segment, a backslash or a NUL byte is refused. A
  release that contains a symbolic link is refused, and links are never followed.
- Downloaded code is never executed.
- Every write is staged next to its target and renamed into place once all of them are
  staged; a failure while staging leaves every original file.
- The env files, the product paths and the manifests are never written.
- The temporary directory is removed in every case.

## A removed showcase stays removed

After `npm run remove:showcase`, `removedCapabilities` holds `"showcase"`. Every
release is stripped of the showcase page, tests, strings and route before the
comparison, so an update never brings it back and reports no conflict for the removed
files. If a release reaches the showcase outside its removal markers, the affected file
is kept and reported as a conflict instead.

## A typical update

```bash
git status                              # start from a clean tree
npm run core:check
npm run core:update
npm install                             # when the report lists manifest changes
npm run lint && npm run typecheck && npm test
git add -A && git commit
```

Commit the update on its own, so `git diff` shows exactly what it changed.
